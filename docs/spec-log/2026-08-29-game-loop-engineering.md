# SPEC壁打ちログ: ゲームループへの固定タイムステップ方式の導入(ループエンジニアリング)

- 起票日: 2026-08-29
- 関連SPEC項目: NFR-8(新規)、AC-10・AC-11(新規)、6章、12章
- ステータス: 決定済み
- 参加: ユーザー / Claude

## 背景・きっかけ

ユーザーから「このアプリにループエンジニアリングを入れたい。簡単に試せる手順を教えて」との依頼。
「ループエンジニアリング」という語が曖昧(ゲームループ自体の改善なのか、AIによるテスト自動修正
ループのような開発ワークフローの話なのか)だったため、選択肢を提示して確認した。

## 論点

- 「ループエンジニアリング」が指す対象の特定。
- 現行のゲームループ(`ui_curses.py` の `run()`)の課題: `time.sleep(0.02)` による単純な
  ポーリングで、重力の自然落下(`game.tick()`)の呼び出しタイミングがcursesループの実行
  時刻に直接依存しており、環境の処理速度差やフレーム落ちで進行が揺れうる。また、ループ
  制御ロジックがcursesの実行関数に埋め込まれており単体テストができない。
- 改善方式の選定(固定タイムステップ+アキュムレータ方式 vs 現状維持 vs 開発ワークフロー
  としてのループ導入)。
- タイムステップ制御ロジックをcurses非依存にしてpytestで検証可能にするか。
- 処理落ちやデバッガ停止等で1フレームの経過時間が極端に大きくなった場合の対策
  (スパイラル・オブ・デス)の要否。

## 検討した選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A. 固定タイムステップ+アキュムレータ | 経過時間をアキュムレータへ蓄積し、一定間隔ごとに `game.tick()` を呼ぶ。フレームレート制御(`sleep`時間の計算)は別クラスに分離 | 決定論的な更新頻度、フレームレートに非依存、ロジックをcurses非依存にでき単体テスト可能 | 実装がやや複雑になる(アキュムレータ・クランプ処理が必要) |
| B. 現状維持(sleepと時刻比較) | 現行の `time.sleep(0.02)` + `if 経過時間 >= interval: tick()` | 変更コストなし | 更新と描画が結合。極端な遅延時に多重更新の制御がない。curses実行関数に埋め込まれ単体テスト不能 |
| C. AIによる自動テスト修正ループの導入 | pytest失敗時にClaudeがテスト実行→失敗検出→修正→再実行を自動で繰り返す開発ワークフロー | 開発効率が上がる可能性 | 今回ユーザーが確認質問で「ゲームループの改善」を明示的に選択したため対象外(別テーマ) |

## やり取りの要旨

- Claude の問い「『ループエンジニアリング』とは具体的にどれを指しているか(ゲームループの
  改善 / AIによる自動改善ループ / その他)」→: ユーザー「ゲームループの改善(推奨)」を選択。
- ユーザーから追加で「開発手法の方も教えて」との依頼(実装の進め方=仕様駆動開発の手順自体も
  説明してほしいという要望)。

## 決定事項

- `src/tetris_cli/game_loop.py` を新規実装(curses非依存)。
  - `FixedTimestepLoop`: `update_interval` を用いたアキュムレータ方式で、渡された経過時間
    から実行すべき更新(tick)回数を返す。1回に蓄積できる経過時間の上限を
    `MAX_FRAME_TIME = 0.25` 秒とし、スパイラル・オブ・デスを防止する。
  - `FrameLimiter`: 目標フレームレート(`target_fps`)から1フレームの予算
    (`frame_budget`)を求め、実際にかかった時間との差分から眠るべき時間を計算する
    (`time.sleep` 自体は呼び出し側=`ui_curses.py` が行う)。
- `ui_curses.py` の `run()` を「1. 入力処理 → 2. 固定タイムステップでの更新
  (`timestep.advance()` が返す回数だけ `game.tick()`) → 3. 描画 → 4. フレームレート制御
  (`limiter.sleep_duration()`)」の4段階に明確化した。目標フレームレートは
  `TARGET_FPS = 50.0` とした。
- `game.gravity_interval()`(レベルアップで短縮される)は毎フレーム
  `timestep.update_interval` へ反映し、レベルアップ後の重力加速を正しく追従させる。
- タイムステップ制御ロジックは `tests/test_game_loop.py` で単体テスト可能にした
  (AC-10, AC-11に対応)。

## 根拠

- 案Bは重力更新のタイミングがcursesの実行ループに直接結合しており、実行環境の処理速度差や
  フレーム落ちで進行が揺れやすく、かつcursesループ内に埋め込まれているため単体テストが
  できない。案Aは業界標準的なゲームループパターン(固定タイムステップ+アキュムレータ)で
  あり、決定論的な更新頻度を保証しつつロジックをcurses非依存にできるため採用した。
- 案Cはユーザーが確認質問で明示的に「ゲームループの改善」を選んだため今回は対象外とした
  (AIによる自動テスト修正ループが必要になれば、別テーマとして改めて壁打ちする)。
