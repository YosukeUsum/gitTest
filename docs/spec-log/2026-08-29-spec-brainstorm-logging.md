# SPEC壁打ちログ: SPEC.md 変更時の壁打ちログを残す仕組み

- 起票日: 2026-08-29
- 関連SPEC項目: 新規（→ NFR-7 として追加）、11章・12章を更新
- ステータス: 決定済み
- 参加: ユーザー / Claude

## 背景・きっかけ

ユーザーから「SPEC.md を更新する上で Claude は壁打ち（設計の論点出し・比較検討）をする必要がある。
その壁打ちの過程をログとして残したい。ただし通常のチャットは残さなくてよい。仕様も含めて決めてほしい」
という依頼があった。既存のプロジェクトは仕様駆動開発で、実装のトレーサビリティは
SPEC.md ↔ tests ↔ 実装で取れているが、「なぜその要件にしたか」という意思決定の記録は残っていなかった。
NFR-6 で「pytest 実行 1 回 = 1 ログファイル」という前例があるため、これに倣った運用を設計する。

## 論点

- どこに何形式で残すか（Git 管理下か生成物か）
- 記録の粒度（セッション単位 / テーマ単位 / 時系列 append）
- 何を「壁打ち」とみなし記録対象にするか。通常チャットとの線引き
- 記録の起票・追記・完了のタイミング
- 運用ルールだけにするか、フックで機械的に強制するか

## 検討した選択肢

| 論点 | 案A | 案B | 採否 |
|---|---|---|---|
| 保存先 | `docs/spec-log/` に Markdown、Git コミット対象 | `logs/` に生成物として出力、コミット除外 | **A**（判断根拠は資産。差分レビュー可能にしたい） |
| 粒度 | 1テーマ=1ファイル、後日分は同ファイルに追記 | 1セッション=1ファイル | **A**（テーマ単位のほうが後から追いやすい） |
| 記録内容 | 論点・選択肢・回答の要旨・決定・根拠 | チャット逐語トランスクリプト | **A**（逐語はノイズが多くトークンも消費、要旨で十分） |
| 強制手段 | CLAUDE.md の運用ルール（毎セッション読み込み） | PreToolUse フックで SPEC.md 編集をブロック | **A**を採用、Bは任意（フックは誤検知で作業が止まるリスク） |

## やり取りの要旨

- Claude: docs フォルダは空・Git 管理外で意味がないと確認 →: ユーザー、そこに SPEC 関連資料（xlsx/pptx 等）を
  置いて SPEC.md 更新の補助に使いたい意向。
- Claude: xlsx/pptx は Read で直接読めず変換が要る、テキスト/CSV/PDF/画像が確実と説明。
- ユーザー: それを踏まえ「壁打ちのログを残す仕組みを、仕様含めて決めて」と依頼。
- Claude: NFR-6（pytest ログ）に倣い、テーマ単位の Markdown ログを `docs/spec-log/` にコミットする案を提示し採用。

## 決定事項

- `SPEC.md` の FR/NFR/AC・方針を追加/変更/削除する際は、事前に壁打ちを行い、その要旨を
  `docs/spec-log/YYYY-MM-DD-<topic-slug>.md`（起票日付き、1テーマ1ファイル）に記録する。
- ログは Git コミット対象。生成物の `logs/`（NFR-6）とは別扱い。
- 記録対象は「SPEC.md の要件・方針に関わる壁打ち」のみ。通常の Q&A・ツール操作補助・
  コードのみの作業・雑談・チャット逐語は記録しない。
- 起票・追記・完了のタイミング、雛形、索引（`docs/spec-log/README.md`）の運用は `CLAUDE.md` に明記する。
- 誤字修正・体裁整形のみの SPEC.md 変更は壁打ちログ不要。
- 機械的強制（フック）は初期導入しない。ユーザー希望時に追加検討。
- 上記を `SPEC.md` に **NFR-7** として明文化し、11章（開発プロセス）と 12章（改訂履歴）を更新する。

## 根拠

- NFR-6 で確立した「1 実行 = 1 ファイル」「日時を含む一意名」「上書きしない」というプロジェクトの
  ログ文化と整合させると、学習コストが低い。
- 壁打ちログはテスト実行ログと違い「意思決定の根拠」であり、時間が経つほど価値が上がる資産なので
  生成物扱いにせず Git で共有・レビュー可能にする。
- フックによる強制は、SPEC.md への軽微編集や、壁打ちログ作成前の下書き編集まで止めてしまい
  開発体験を損なうため見送り。運用ルール（CLAUDE.md）で十分な統制効果が得られる。
