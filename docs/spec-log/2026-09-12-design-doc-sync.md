# SPEC壁打ちログ: SPEC.md変更時にdocs/design/の説明資料も同期更新する

- 起票日: 2026-09-12
- 関連SPEC項目: NFR-12(新規), 6章, 11章, 12章
- ステータス: 決定済み
- 参加: ユーザー / Claude

## 背景・きっかけ

「このアプリを知らない人にも説明できるように」との要望で `docs/design/` に
概要資料(pptx)・設計書(docx)・要件一覧(xlsx)の3点を新規作成し、Cowork上のスキル
「design-doc-sync」として今後の更新手順を提案した(前セッション)。

その直後、ユーザーから「仕様が変わったらドキュメントも新規作成、変更することは
仕様なので認識しておいて」との指示があった。これは、3資料の同期更新が単なる
Cowork運用上のスキル(ツール側の手順)にとどまらず、`SPEC.md` 自体が定める
プロジェクトの仕様(要件)の一部であるべき、という意味だと解釈した。

NFR-7が「SPEC.md変更時に壁打ちログを残すこと」をSPEC.mdで明文化しているのと
同様に、「SPEC.md変更時にdocs/design/の説明資料も更新すること」もSPEC.mdの
非機能要件として明文化するのが一貫性がある。

## 論点

- 説明資料の同期更新を、SPEC.mdの正式な要件(NFR)として明文化すべきか、
  CLAUDE.md(作業ルール)やCowork スキルの記述だけに留めるべきか。
- 明文化する場合、既存のNFR-7(壁打ちログ運用)と統合するか、独立した新規NFRにするか。

## 検討した選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A | 独立した新規NFR(NFR-12)として追加 | NFR-7(壁打ちログの記録)と目的が異なる(こちらは対外説明資料の同期)ため責務が明確。将来どちらかだけを見直す場合も影響範囲が分けやすい | SPEC.mdの項目数が増える |
| B | NFR-7に追記して1項目にまとめる | 項目数が増えない | 「壁打ちログを残すこと」と「説明資料を更新すること」は別の成果物・別のタイミング(後者は壁打ち完了後)で行う作業であり、1つのNFRに混在させると読みにくい |
| C | SPEC.mdには書かず、CLAUDE.mdとCoworkスキルの記述のみに留める | SPEC.mdをシンプルに保てる | ユーザーの「これは仕様である」という明示的な指示に反する。SPEC.mdが実装・テストの拠り所であるという本プロジェクトの前提(1章・CLAUDE.md冒頭)から外れる |

## やり取りの要旨

- ユーザー: 「仕様が変わったらドキュメントも新規作成、変更することは仕様なので認識しておいて」
- Claude: NFR-7と同様の位置付けで、独立したNFR(NFR-12)としてSPEC.mdに明文化する方針で進めることとした。

## 決定事項

- SPEC.md 5章に **NFR-12** を新規追加する: 「SPEC.md の FR/NFR/AC を追加/変更/削除する際は、
  NFR-7の壁打ちログ運用に加えて、`docs/design/` 配下の説明資料(概要資料pptx・設計書docx・
  要件一覧xlsx)についても当該変更を反映するよう作成・更新すること。個別の生成・更新手順は
  Cowork上のスキル『design-doc-sync』を参照する。」
- SPEC.md 6章のアーキテクチャ図に `docs/design/`(説明資料、NFR-12、Git管理下)を追記する。
- SPEC.md 11章の開発プロセス(手順6)に、説明資料の更新も併せて行う旨を追記する。
- CLAUDE.md の「SPEC.md を変更するときの手順」にも、説明資料の更新ステップを追加する。

## 根拠

- 本プロジェクトはSPEC.mdを実装・テストの拠り所とする仕様駆動開発であり(1章・CLAUDE.md冒頭)、
  「対外説明資料を最新に保つ」という継続的な運用ルールも、ユーザーが明示的に「仕様である」と
  述べた以上、口頭合意やツール側のスキルだけでなくSPEC.md自身に明文化するのが本プロジェクトの
  一貫した方針(NFR-7も同じ理由でSPEC.md化されている)に合致する。
- 独立NFR(案A)を選んだのは、NFR-7(壁打ちログという「議論の記録」)と本要件(「対外説明資料と
  いう別成果物の同期」)は目的・成果物・タイミングが異なり、1項目に混在させるとSPEC.mdの
  可読性・保守性が落ちるため。
